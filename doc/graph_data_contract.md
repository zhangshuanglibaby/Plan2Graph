# 任务图数据约定（阶段 0.5 草稿）

本文只约定数据的含义，不表示提取、校验或生成任务图的功能已经实现。

## 1. 模型提出的数据

模型将来返回两个列表：`tasks`（任务）和 `relations`（关系）。

每个任务包含：

| 字段 | 含义 |
| --- | --- |
| `ref` | 本次回答中引用任务的临时名称，不是最终图编号 |
| `title` | 简短的任务标题 |
| `source_quote` | 输入计划中提到该任务的原文片段 |

每条关系包含：

| 字段 | 含义 |
| --- | --- |
| `before` | 前置任务的 `ref` |
| `after` | 后续任务的 `ref` |
| `kind` | `hard`（确定依赖）或 `candidate`（待确认关系） |
| `source_quote` | 输入计划中涉及这条关系的原文片段 |
| `reason` | 为什么判为确定依赖，或需要确认什么 |

箭头始终从 `before` 指向 `after`。例如“A 依赖 B”表示 B 在前、A 在后。模型不能自行决定最终的 `T1`、`T2` 编号，也不能直接返回 Mermaid 图。

## 2. 程序内部的任务图

内部任务使用程序分配的 `T1`、`T2` 等编号。明显重复的任务将来合并时，要保留其原文依据。没有任何关系的任务也必须保留。

内部关系保留方向、`hard` 或 `candidate` 类型、原文依据及原因。被跳过的关系另行记录其两端和跳过原因，不能把它当成已经画出的关系。

任务编号将来按任务在输入原文中首次出现的位置分配；这个位置由程序核对原文后确定，不相信模型自行提供的位置。

## 3. 小样例

输入提到“支付对接依赖订单接口”，还单独要求“编写发布说明”。

应能表示三个任务：订单接口、支付对接、编写发布说明；一条确定关系“订单接口 → 支付对接”；“编写发布说明”没有连线，但不能丢失。

“最好先做 A 再做 B，但也许能并行”不能直接记为确定依赖；若值得询问，可记为待确认关系并写明问题。

## 4. 本阶段边界

本文件只定义数据含义。原文引句核对、任务合并、环检测、Mermaid 生成和 DeepSeek 调用均尚未实现。
