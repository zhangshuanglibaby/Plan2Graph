## 评估集合与边界

- 评估前固定样例清单：每条记录唯一的标注文件、标注中的 `原计划：` 路径、来源类型、主覆盖类型和是否允许传输给模型。当前 20 份标注及对应计划副本位于 `server/tests/fixtures/`；两份计划经用户确认曾由 Agent 输出，18 份为合成。旧八份未找回，不计入。

## 四项指标

| 指标 | 本地计数方式 | PRD MVP 目标 |
| --- | --- | --- |
| 成功输出的结构有效率 | 本轮成功出图中，通过任务 ID 唯一、边端点存在、无自依赖、展示图无环等检查的输出数 / 本轮成功出图数 | 100% |
| 任务覆盖率 | 本轮已运行样例中，被正确提取的人工关键任务数 / 这些样例的人工关键任务总数；没有成功图的样例计 0 个已覆盖任务，并单列失败原因 | >= 90% |
| 无依据的确定依赖率 | 本轮成功图中，经人工判为无依据的实线边数 / 这些图实际输出的全部实线边数 | <= 10% |
| Mermaid 可渲染率 | 本轮成功出图中，交由实际 Mermaid 渲染器解析并成功渲染的输出数 / 本轮成功出图数；未执行渲染的图不能算通过 | 100% |

按所有已运行样例合计分子、分母后计算，不取各样例百分比的简单平均。任一分母为 0，结果记“不适用”并写明原始计数，不写成 100%；若有成功图却未执行结构检查或渲染，相应指标记“未完成核验”，不以已检查子集冒充全体成功输出。结构有效只证明图形式合法，不证明关系语义正确；模型 JSON 可解析或 Mermaid 源码可生成，不等于实际渲染成功。

## 人工对齐与错例

- 逐条以标注中的“关键任务”为金标准。用原文工作项、标题含义与实际交付物人工做一对一匹配，不要求标题逐字相同；一个输出节点最多覆盖一个关键任务，一个关键任务最多计一次。重复表述按标注合并后计一次；拆成多个同义节点不重复加分，把不同关键任务合成一个模糊节点也不能覆盖多个。无法判定的匹配记录争议，复核前不计“正确提取”。
- 记录漏任务、无依据新增任务、重复节点及错误合并的数量和具体对应关系，作为诊断，不偷换 PRD 的任务覆盖率分母。无依赖样例仍计全部人工关键任务。
- 对每条实际输出的实线，先映射两端到人工关键任务，再检查方向、原文证据及人工标注的确定/候选/禁止/争议判定。反向、凭建议顺序升级为硬依赖、候选或冲突关系未经裁决画成硬依赖、端点不属于计划任务及原文不支持的额外前置关系，均记录为无依据实线；仅引文存在不能自动证明依赖成立。不能自动裁决的语义争议单列待复核，不得先标为有依据以提高指标。实际输出的重复边也单列为图质量问题，不凭去重后的数量替代“全部实线边”。
- 候选虚线可画也可不画的样例，不以漏画虚线计入上述四项；但候选变实线属于无依据实线。另列候选边方向错误、冲突未提示及不应有边等问题，保留原始失败案例。矛盾样例中，明确报冲突并停止出图可以符合人工标注的允许路径，但不是“成功输出”，也不算结构或渲染通过；单列这一结果及其对端到端任务覆盖的影响。

## 离线输入记录与执行入口

脚本以每条样例每次运行一份结构化记录为输入，不通过调用模型补齐缺失数据，也不从 Mermaid 源码反推图证据。输入文件为 UTF-8 JSON，顶层仅含 `records` 非空数组；每条记录为对象，拒绝重复键和非标准数值。以下路径均相对 `server/`：

| 字段组 | 必需内容与约束 |
| --- | --- |
| 身份与来源 | `case_id` 使用标注文件名去掉 `_annotation.md` 的部分；`annotation_path`、`plan_path` 指向当前仓库文件，分别保留原始字节的 `annotation_sha256`、`plan_sha256` 内容指纹；原计划路径还须与对应标注中唯一的 `原计划：` 声明一致；实际运行时用必填的 `run_id` 区分不同批次，未运行可无；`source` 区分未运行（无输出来源）、本地离线构造、历史记录和本轮真实调用。历史及构造记录不得混入本轮真实模型质量指标 |
| 金标准 | `gold_tasks` 为按标注“关键任务”顺序排列的 `{id, title}` 对象数组，编号从 1 连续；必须逐项吻合当前标注小节，重复表述合并后只留一项；人工裁定边仍以标注原文为准 |
| 运行信息 | `status` 只能为未运行、成功出图、明确冲突停止或其他失败；未运行必填 `reason`，不可填运行信息、图及裁定；已运行必填 `execution` 对象，字段恰为 `exit_code`（非负整数或 `null`）、`error_category`（成功为 `null`，失败为非空文本）、`timestamp`、`code_version`、`prompt_version`、`model_alias`、`server_version`、`request_parameters`（对象），另有 `diagnostics` 文本数组（失败非空）；无法核实的元信息写“未确认”，不得臆造 |
| 成功图 | `graph` 快照含 `tasks`、`relations`、`skipped_relations` 三个数组；任务字段为 `id`、`title`、`source_quotes`、`first_position`；展示关系字段为 `before`、`after`、`kind`（`hard` / `candidate`）、`source_quote`、`reason`；跳过关系含 `relation` 与 `skip_reason`。另存当次 `mermaid_text`；失败或未运行不可伪造图 |
| 人工任务对齐 | `task_alignment` 为每个实际输出任务列表位置恰一条 `{task_index, gold_id, reason}`；`gold_id` 为人工匹配的金标准编号，或文本“未匹配”，且 `reason` 非空；重复编号、漏项与待复核裁定拒绝发布 |
| 人工实线裁定 | `hard_edge_verdicts` 为每条实际输出的 `hard` 关系恰一条 `{relation_index, verdict, reason}`；`relation_index` 是原关系列表从零开始的位置，`verdict` 最终仅可为“有依据”或“无依据”，理由非空；待复核需保留争议但不可用来发布完整计数 |
| 渲染核验 | 运行命令会用指定的本地 `mmdc` 重新渲染每张成功图，记录 `render_check` 的 `status`、`renderer`、`renderer_version`、`source_sha256` 和 `failure_reason`；输入文件自带的旧渲染状态会被本次结果覆盖。渲染失败仍占成功图分母；未运行/失败样例无需渲染 |

在 `server/` 下以 `./.venv/bin/python -m plan2graph.evaluation /绝对路径/records.json --run-id 本轮批次 --renderer /绝对路径/mmdc --mode synthetic` 运行本地合成记录评估；`--mode current` 仅接受自称“本轮真实调用”的同批次记录，不会自行采集模型输出，更不能证明来源真实。命令将完整逐例状态、人工裁定、失败诊断及四项汇总写到标准输出的 JSON 报告；缺字段或缺裁定时报错且不发布部分指标。成功图的 ID 格式及唯一性、端点、自依赖和环分别检查：即使结构无效，也留在成功输出分母；零分母的 `rate` 为 `null`，未运行不计入本轮质量分母。`provenance_verified` 与 `acceptance_ready` 目前始终为 `false`，不能将 JSON 中的来源字段、文件指纹或合成测试当作真实调用证据。当前环境未找到 `mmdc`，因而没有在本轮执行官方 Mermaid 渲染；测试中的渲染器是模拟进程。任务与边的语义裁定仍需人工完成。

### 现有数据出口的静态核对

`src/plan2graph/models.py` 的 `PlanGraph` 包含 `tasks`、`relations` 和 `skipped_relations`：任务有 ID、标题、多处原文引文与首次位置；关系有两端、`hard`/`candidate` 类型、引文和原因；跳过记录另有原因。这些字段对应上表的 JSON 快照。`src/plan2graph/cli.py` 的成功出口只把 Mermaid 源码写到标准输出或 `-o` 文件，把数量、候选关系及跳过关系诊断写到标准错误；CLI 并不输出完整 `PlanGraph`。因此不能仅凭 `.mmd` 或 CLI 文本反推任务引文、原文位置及全部关系证据，更不能把手工猜出的字段冒充真实运行快照。离线评估器可以读取完整快照，但可信的真实运行采集及同次关联仍待实现和授权。

`src/plan2graph/extract.py` 的 `extract_plan_graph(plan_text, client)` 在成功时直接返回 `PlanGraph`，`src/plan2graph/mermaid.py` 的 `render_mermaid(graph)` 可从同一对象生成源码。因此后续可考虑由独立采集入口在**一次**获授权的抽取中保存结构化图及对应源码，再交给不联网的离线评估脚本读取；不为补全记录重放请求，不从 CLI 的 Mermaid 文本逆推证据。若采用该入口，还须与现有 CLI 对齐输入非空、长度上限和配置检查，并如实记录失败、诊断及运行参数；它尚未实现，不能称为已验证的 CLI 等价运行。没有具体计划的传输许可和运行授权前，不执行采集。

### 一份合成样例的静态核对

以 `tests/fixtures/paraphrased_duplicate_task_annotation.md` 及其所指的 `tests/fixtures/plans/收藏列表接口-同义重复合成样例.md` 为例，`case_id` 可取 `paraphrased_duplicate_task`。标注的金标准为 4 个关键任务：新增表、列表查询接口、页面接入、冒烟测试；原文工作项 2 与 4 同属第 2 个关键任务，不能凭原文有 5 个编号就把 `gold_tasks` 写成 5 项。标注有三条确定边，按金标准编号为 1 → 2、2 → 3、3 → 4；没有候选边，禁止为重复的工作项 4 单独建节点。

这次只核对了身份、原计划引用和金标准的表达能力。此例仍为“未运行（无输出来源）”，没有 `run_id`、模型图、任务匹配、实线裁定或渲染结果；上述三条是人工标注，**不是模型输出**，不能计入任何本轮质量指标。成功图字段是否足以承载真实输出，仍待后续获授权的运行或独立的离线构造数据核验。

### 一份矛盾样例的静态核对

`tests/fixtures/three_task_cycle_conflict_annotation.md` 指向 `tests/fixtures/plans/角色权限配置-三任务环形矛盾合成样例.md`，对应 `case_id` 为 `three_task_cycle_conflict`。金标准有 3 个关键任务；原文声称的 1 → 2、2 → 3、3 → 1 合成一个环，没有经原文裁决的确定依赖集合。这三条是**待诊断的原文关系**，不能作为某次成功图已输出的三条实线。

此样例目前也是“未运行（无输出来源）”，没有实际退出码、图或冲突诊断。将来若实际运行明确报告完整环路冲突并停止出图，才记录为“明确冲突停止”，保存真实错误类别与诊断；它计入已运行样例及任务覆盖率分母，但无成功图可匹配时覆盖任务数为 0，不进入以成功图为分母的结构有效率和渲染率，也没有实线可计。若实际返回成功图，须单独检查是否明确提示整体冲突、是否将未裁决关系误作实线及图结构是否有效；静默删边或单凭无环不能算处理了矛盾。标注允许的两条路径均非已观测结果，不能提前记为通过。
